## 安装、版本与完整回归

实际环境为 **macOS 27.0.1 / Apple arm64、CPython 3.12.14、Streamlit 1.66.0、openpyxl 3.1.5、defusedxml 0.7.1**。基础解释器来自本机 Codex runtime；PATH 中没有 `python3.12`，README 命令的前提是使用者已安装并配置 Python 3.12。系统 Python 3.9 不满足要求。

早先 `.venv-m4-clean` 使用临时 wheelhouse 完成安装，历史输出见 [m4-install.txt](m4-install.txt)。最终复验时 `/private/tmp/sheetcheck-m3-wheels` 已不存在，校验因此以 `Wheelhouse is incomplete.` 退出，没有改写成功证据。随后按原 `requirements.lock` 从 PyPI 重新取得 43 个 wheel，存入 `outputs/m4/wheelhouse`，没有修改锁文件或放宽哈希检查。

重新取得依赖是一次**联网准备**。首次受限命令因 DNS 不可用失败，保留 [沙箱失败输出](m4-wheelhouse-refresh-sandbox.txt)；获准联网后的重试成功，见 [下载输出](m4-wheelhouse-refresh.txt) 和 [取得依赖记录](m4-wheelhouse-refresh.json)。这与浏览器下载授权循环是两个不同事件，不能混淆。

全新 `.venv-m4-release` 创建前不存在，`include-system-site-packages=false`。实际从本地 wheelhouse 安装的命令如下；其中 `python3.12` 此次使用记录中的基础解释器绝对路径。每一步的完整命令、起止时间和退出码见 [安装记录](m4-release-install.json)、[原始输出](m4-release-install.txt)。

```sh
python3.12 -m venv .venv-m4-release
.venv-m4-release/bin/python -m pip install --no-index --no-cache-dir \
  --find-links outputs/m4/wheelhouse --require-hashes -r requirements.lock
.venv-m4-release/bin/python -m pip install --no-index --no-cache-dir \
  --no-build-isolation --no-deps -e '.[ui,test]'
.venv-m4-release/bin/python -m pip check
.venv-m4-release/bin/python scripts/verify_install.py \
  --wheelhouse outputs/m4/wheelhouse --output docs/m4-release-environment.json
.venv-m4-release/bin/python -m pytest -q
```

安装显式设置 `PIP_DISABLE_PIP_VERSION_CHECK=1`、`PIP_NO_INDEX=1`、`PIP_CONFIG_FILE=/dev/null`。43 个依赖和唯一额外发行包 SheetCheck 与预期相符，`pip check` 返回 `No broken requirements found.`；wheel 哈希、内部元数据、平台标签、安装版本和实际配置均通过。早先负向控制更改一个 wheel 后，校验器拒绝且未产生成功证据，仍按历史执行属性保留。

## 应用范围断外网流程

此项实际应用版本为 **0.3.0**。使用 [loopback-only.sb](../scripts/loopback-only.sb) 和 [acceptance_offline.py](../scripts/acceptance_offline.py)，在 `127.0.0.1:8502` 启动正常 Streamlit 应用，HTTP/WS 外层增加 CSP 与不含业务值的请求分类记录；普通启动仍使用回环地址 8501。

向数值 TEST-NET 地址发起 IPv4 / IPv6 TCP 正向控制，两次均返回 OS 策略拒绝 `errno=1`，不是超时或无路由。浏览器主动请求外部图片的控制页被强制 CSP 阻止，并回送 `img-src` 违例。随后冷加载本机页面，用文件选择器实际上传虚构 `orders.csv` 和 `payments.xlsx`，完成映射、规则确认、核对、生成报告与浏览器下载。

[网络事件](m4-network-events.jsonl) 中，控制阶段后没有 Python `socket.connect` 或 `getaddrinfo` 事件，业务页面没有 CSP 违例；记录到 141 次静态资源 200、2 次上传 204、2 次下载 200。这些是请求次数，不代表两次独立业务运行。详细记录见 [断网结果](m4-offline-result.json)、[说明](m4-offline.md)、[截图](m4-offline.png)、[服务日志](m4-offline-server.log)。

实际下载的 [混合输入报告](../outputs/m4/sheetcheck_20261023T172102Z_11d5df5da13342789b9206f52bcf004a.xlsx) 为 **19,249 字节**，SHA-256：

```text
a90cb4b8c24fd9082b2f4b897de64b4b0be4d995f24e057771d06a6fbde98a87
```

该文件用原 CSV/XLSX 独立重新读取、核对和回读，指纹及手工样例金额一致，包含完整 5 条业务结果、3 条异常、6 条问题、14 条账本。完整交付结论依赖取得的字节、哈希和复算，不只依赖 HTTP 200 或下载按钮。

结论限于**应用进程 OS 限制 + 浏览器页资源 CSP 的应用范围断外网验收**。Mac 保持联网，未关闭 Wi-Fi，也未进行 pcap。Python audit hook 不是全部系统或原生扩展网络调用的观察器；CSP 不涵盖浏览器其他页面、后台服务或顶层导航；回环服务仍允许。额外 CSP 与 `sandbox-exec` 是测试夹具，普通启动不自动获得该策略，`sandbox-exec` 不是产品依赖。

## 日志、留存与安全

[日志安全记录](m4-log-security.md) 保留候选针对回归：日志/CLI/页面 **85 passed in 41.28s**，公式注入/坏文件/回读 **226 passed in 48.29s**，原始输出分别为 [日志测试](m4-log-tests.txt)、[安全测试](m4-security-tests.txt)。这些用例已纳入最终 1.0.0 的 502 项回归，不额外累加。

32 项新增测试用独特虚构编号、金额、备注和文件名 canary，检查正常流程、真实坏 CSV/XLSX、读入/校验/核对/导出/渲染失败、CLI JSON 序列化失败、非法参数、陈旧下载和 Streamlit deferred manager 实际异常包装。模拟底层异常携带 canary，日志和 stderr 不回显；业务 JSON/UI/报告保留原值作为正向控制。

页面 logger 只记阶段、固定错误码和版本；CLI 错误只给固定诊断与恢复文字，成功 stderr 为 `code=EXPORTED stage=EXPORT version=...`。主动请求的 JSON、UI 预览和 XLSX 是业务输出，不混称为日志。既有测试覆盖危险公式前缀、超链接/外链/宏/活动内容、损坏 ZIP/XML、实体、伪装文件、映射公式，以及报告身份、金额、源行和零/缺失值篡改。

依赖预载后，CSV/XLSX 完整流程在禁止文件打开及 tempfile API 的条件下通过。默认不保存业务文件或跨会话缓存；主动下载或 `--export-dir` 保存由用户管理。重置释放应用引用并禁止旧操作提交，不承诺抢占已开始的 CPU 计算、清空框架全部引用或安全擦除 RAM、交换区和下载记录。没有自动墙钟超时，验收器子进程超时不是产品自动取消机制。

## 容量、性能和未达目标

方法和命令见 [容量性能说明](m4-capacity.md)。实测硬件为 Apple M4、10 个逻辑 CPU、24 GiB 内存，来源是实际系统查询；安装 JSON 内部分受限字段如实为 `unavailable`。默认边界和早期负载为 **0.3.0 开发快照**；最终追加 XLSX 10k 三轮 / 50k 一轮为 **1.0.0**，使用 `.venv-m4-release`，两组证据分开保留。

### 默认容量

[m4-capacity-results.json](m4-capacity-results.json) 为 **20/20 passed**。CSV/XLSX 分别覆盖恰好 10 MiB / 多 1 字节、50,000 记录 / 多 1 条、100 列 / 多 1 列；XLSX 另覆盖解压总量 100 MiB、2000 条目、200:1 压缩比、128 层 XML 的恰限及超限。没有降低默认限制或伪造 ZIP 长度；超限以对应错误码拒绝，不截断后计算；20 例均无超时。

这些是独立维度读取验收，不是 `50,000 行 × 100 列 × 最大字段` 组合压力，也不覆盖全部宽表、共享字符串、样式及并发会话。最终 502 项包含较快的默认边界回归与基准超时不能标记成功的测试。

每轮为新子进程。输入构造不计入阶段时间，但计入进程 RSS；核心包含校验、核对和内核审计；导出包含强制回读；额外 standalone 回读是验收时多做的一次审计。`ru_maxrss` 为子进程累计高水位，不是阶段增量，也不含浏览器和 Streamlit 服务。其他桌面程序存在，不能称为独占空闲机器。

### 对象生命周期修复与瓶颈

修复前 [引用探针](m4-benchmark-workbook-reference-probe.json) 证实强制回读开始时五张写出工作表和单元格仍可达，现场 `gc.collect()` 无法释放仍被局部 sheet 引用的 workbook。该探针替换审计函数，仅证明生命周期问题，不替代正确性测试。

修复将写出移入 `_write_xlsx()` 独立作用域，返回后回收不可达对象，再执行原有 `audit_xlsx()`。`test_export_releases_workbook_before_mandatory_readback` 关闭自动循环回收、连续导出两次，在真实回读入口检查 workbook 弱引用已消失，再继续真实审计；该用例在最终两个环境均通过。没有减少字段、删行、跳过审计或放宽规则。

修复后单轮 CPU 秒为读取 **0.680**、核心 **0.264**、导出含回读 **16.639**、额外回读 **7.140**，分别约占墙钟的 99.6%、99.3%、98.6%、98.2%。本轮主要耗时在静态工作簿写出和安全回读，而非编号配对。没有进一步 profiling 写入、ZIP/XML 和回读内部步骤，不能给出未测的细分占比。

这不是受控 A/B 实验：前后日期、桌面负载和代码不同，原始组没有 CPU 时间，不能把提速全部归因于释放修复，也不能断言原 3.094 秒波动由某个程序造成。早先修复后单轮峰值 429.59 MiB、最终 1.0.0 三轮最高 430.00 MiB，均高于原 XLSX 10k 的 378.88–413.20 MiB，**没有测得整流程峰值下降**。已证实的是写出对象不再与回读重叠保留；写出阶段仍一次构建完整格式化工作簿。

蓝图把每侧 10k 的 3 秒 / 512 MiB 写作建议目标，要求实测并分析未达项，不是所有机器及最大输入的服务保证。最终 XLSX 10k 三轮达到建议、50k 完整功能通过，与原 3.094 秒历史未达记录和最终 50k 约 1.91 GiB 的资源需求同时成立；不以一个“全绿”标签抹平这些区别。
